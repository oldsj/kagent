# Native workspace preparation

`SessionService.PrepareSessionWorkspace` prepares an owned Mainloop code Session before its first native turn. It runs checkout and fixed role setup through the installed Claude or Codex executor without invoking `Run`, creating a native Session/thread, binding continuation history, or sending an A2A message. Existing startup CLI version validation remains separate from preparation.

## Authority and immutable inputs

The public mutation requires the verified Mainloop service principal and an explicit Session policy permitting `update` for the original creator, Agent and namespace. Shares and runtime principals cannot request preparation. Authorized `GetSession` reads retain their existing `read` boundary; shares and collection/lifecycle responses do not receive the preparation receipt.

The request binds the original Create request ID, Session, full source commit SHA and named branch, D image/platform/policy identity, controller-selected R, prepared revision, active runtime generation and Actor UID. The service reads the exact current Actor and its original immutable template, checks the retained composition snapshot, enforcing Git proxy configuration and original credential references, and fingerprints the compiled configuration and Mainloop MCP setup. Callback assertions never select these values.

The separately digested overlay is fixed `supervisor` or `child` standing context. It instructs discovery through `whoami` then `task_get`, and contains no task facts, owner brief, previous transcript, credential reference or inherited consent. Claude appends it through `append_system_prompt`; Codex uses `developer_instruction`. Original native instructions and compiled MCP configuration remain the base. Claude preserves compiler-selected `RequireApproval` protection through its existing authenticated approval broker, permission settings and MCP bridge; constructing those inputs requires no native turn.

## Durable assignment and completion

Migration `000006_native_handoff_actions.sql` stores one bounded supplementary action per Session. The Session row remains the sole admission lock and lifecycle owner; its current operation ID guards pending or uncertain effects and observations. Confirmed setup belongs to the captured runtime generation and Actor UID, so successful ordinary Suspend/Resume preserves preparation and continuation despite replacing the incidental lifecycle operation ID. The action records original request bytes/digest, execution identity, assignment, issue state and receipt; it adds no lifecycle enum or scheduler. Historical evidence survives Session deletion.

Public retries with identical original inputs join the same action. Changed inputs or a different action conflict. The authenticated runtime's existing `TaskStoreService.GetWorkspace` channel issues the assigned action once, committing `uncertain` and the issue timestamp before returning it. Missing callbacks, expiry, pool replacement and process restart cannot issue setup again. Pending or uncertain preparations close task, checkpoint and ordinary lifecycle admission using the existing Session lock.

The shared workspace bootstrapper serializes preparation with turns and durably records the original issue before checkout or overlay installation. It refuses foreign or incomplete Git state rather than resetting it. A completed checkout is observed from actual HEAD, symbolic branch and repository-local transport configuration; a done marker is insufficient. Read and push use the fixed enforcing proxies, inert gateway headers and disabled redirects. Altered remotes, duplicate settings and command overrides fail observation.

The provider installer uses the normal native configuration path while requiring an empty continuation store for the initial effect. It records the fixed overlay/configuration fingerprints and verifies the installed provider configuration during observation. It constructs a configured runner without validating or starting a native process. Claude separately fingerprints its materialized ephemeral MCP and approval settings without persisting the broker token. On restart, validated durable compiler/setup state permits reconstruction of missing ephemeral files and a fresh approval broker. Present files must match the recorded projection before materialization; tampered files fail without overwrite. Startup reconstruction preserves the original setup effect, result/time and continuation. Read-only observations require the installed files and cannot recreate them. The existing executor closer follows the configured runner and closes replaced and final approval brokers. The runtime persists the typed result and observation time before calling `CompleteWorkspacePreparation`; after a lost reply or restart it retries those same result bytes, without repeating checkout or the original setup action.

Completion is runtime-only and uses the existing runtime issuer, audience and active-generation authentication. The service makes a fresh Actor/template observation outside the database transaction; the store then locks the Session and rechecks the original assignment, D/R/source selection, operation owner and captured generation. Exact duplicate results are idempotent; differing duplicates fail. An already authenticated in-flight callback may settle the original action after revocation, but its receipt is historical and cannot restore admission. Revoked credentials cannot authenticate a new callback.

## Observation and admission

A currently valid confirmed action can issue a new bounded read-only challenge with the same execution identity and original inputs, including after successful same-generation Suspend/Resume. The new challenge captures the current lifecycle guard while retaining the original action and effect evidence. The runtime observes Git and setup without checkout, reset, overlay installation or native history creation. Admission closes until that challenge commits. Challenges are limited to 65,535; settled task history is preserved, while active tasks, pending HITL, dispatch, cleanup and checkpoint creation exclude observation. Historical or revoked preparation cannot reopen current authority.

The receipt separates `effect_observed_at` from the latest challenge's `observed_at`. Cached `GetSession` calls return existing evidence without refreshing either time. `pending`, `uncertain`, `definite-failure`, or historical receipts do not establish current readiness. READY state, requested source SHA and local markers alone cannot establish success.

The task store and native wrapper gate the owned Mainloop code profile. An explicit D plus workspace under the Mainloop creator is held until enforcing Git preparation qualifies. Ordinary standalone Sessions and Git-free coordination do not acquire a Mainloop-only prerequisite. This supplementary action provides preparation evidence; the existing dispatch/runtime-generation guards still own current task admission.

## Qualification limits

Local integration tests exercise public authenticated gRPC, real PostgreSQL assignment and callback persistence, installed executors, local Git transport and capturing fake CLI executables. They prove model-free source behavior, both provider hooks, same-generation lifecycle continuation, immutable retry, Claude restart with missing ephemeral files and lost-result reconciliation, protected MCP setup, transaction rollback, admission and revocation races. They do not prove live Actor execution, provider behavior, or deployed Git transport enforcement. Native MCP protection and Mainloop Auto/Approval merge policy remain distinct. All four real Claude/Codex × Auto/Approval task deliveries remain required.

Mainloop handoff integration awaits accepted Mainloop enrollment/publication contracts. Permanent source fencing, preview closure, owner restoration, actual DATA erasure, P4 deployment and enforcement, real native continuation/handoff, live bypass checks, publication review and exact published-head CI remain separate gates. No preparation receipt substitutes for those outcomes.
